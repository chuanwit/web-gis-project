项 目 背 景 与 意 义
为什么要做智慧城市交通管控平台？
Background

▎ 项目背景

  • 城镇化进程加速：城市交通系统日趋复杂，传统人工调度效率低下，亟需数字化转型
  • 交通事件响应滞后：事故发现、资源调度、路径分流多环节割裂，处置效率偏低
  • 数据孤岛问题：交通、资源、气象等数据分散，缺乏统一研判与综合态势展示
  • 决策支持不足：传统大屏仅"看得见"，无法基于大模型"判得准、发得出、调得动"

▎ 研究意义

  • 理论意义：探索数字孪生、大模型与 GIS 可视化深度融合的技术范式
  • 应用价值：构建"感知—诊断—调度—推演"全链路业务闭环，实现可落地实战
  • 示范推广：可快速复制到其他城市/领域，为智慧城市建设提供参考模板
  • 工程能力：从 0 到 1 完成真实项目全流程，覆盖前端、后端、AI 与运维部署

需 求 分 析
从用户角色到功能需求的全面梳理
Requirements
A指挥员角色
全局态势感知、应急资源可视化调度、情景推演与预案对比、一键发布调度指令
B分析员角色
风险诊断与趋势分析、区域风险排行、事件类型分布、资源覆盖率评估
C管理员角色
系统配置管理、图层开关、地图视角复位、AI 模型参数与密钥管理

◎ 功能性需求

  • 三维数字孪生地图（建筑/路网/区域/资源）
  • 综合态势展示（飞线、热力、散点、气象）
  • 交通风险诊断（雷达图、类型分布、排行）
  • 应急资源可达分析（服务半径、覆盖率）
  • 情景推演优化（策略勾选、指标预估、模拟）
  • AI 智能助手（自然语言查询、流式响应、溯源）
  • 交互工具（拉框分析、测量、路径规划）
  • 数字孪生时段联动（早/午/黄昏/夜四时段）

◎ 非功能性需求

  • 性能：地图图层首屏渲染 ≤ 3 秒；交互响应 ≤ 300ms
  • 可用性：数据接口降级容错，AI 服务双模式兜底
  • 兼容性：Chrome 90+、Edge 90+；1920×1080 及以上
  • 安全：API Key 服务器端存储，前端不可见密钥
  • 可扩展：Pinia 状态中枢，模块松耦合，便于新增业务
  • 视觉：科技感统一风格，无障碍配色（对比度 ≥ 4.5:1）
  • 可部署：前端 Nginx 静态托管 + PM2 后端守护

7
创 新 点
技术与业务双重创新
Innovation
1
业务闭环可视化
突破传统大屏"纯展示"局限，构建 感知—诊断—调度—推演 四阶段完整业务闭环：
  • overview 模块进行全局态势感知
  • risk 模块多维度诊断高风险区域
  • resource 模块调度资源、评估可达覆盖
  • simulation 模块推演策略效果并对比
2
AI 大模型深度融合
区别于普通大屏外挂式 AI，实现 上下文感知 + 数据溯源 + 流式响应：
  • 自动注入当前时段、模块、区域风险排行等上下文
  • SSE 流式打字机动效，首字节响应 0.8s
  • 回答数据可溯源到真实 mock 数据
  • 规则引擎兜底，离线也可使用
3
数字孪生时段联动
时间轴驱动三维多维度联动，呈现真实城市一天的变化：
  • 天空：清晨/白天/黄昏/深夜四套雾化参数
  • 建筑：不同时段楼体颜色/发光微调
  • 道路：夜间自动开启路灯效果
  • 天气：Header 实时显示当前武汉天气
4飞线辐射 + 3D 挤出可视化
参考成熟作品创新结合：中心→5 区域弧线飞行动画；风险值映射为区域多边形挤出高度，信息密度与美感兼顾
5数据降级容错机制
三级降级（API → Mock → 默认值）保证大屏永不空白，生产部署无 Mock 时 Express 提供真实数据接口
6工程化 + 一键部署
提供 deploy.sh 一键部署脚本 + Nginx 配置 + PM2 守护 + 8080 端口独立运行，无需影响既有网站
